# 01 · 架构决策（方案 A）

日期：2026-10-24
决策人：发起人（拍板 A）；执行：DSH
状态：已定稿

## 一、背景

两套系统都能独立跑，但定位不同：

- 原作者 v2.12：Windows 电脑端（Node 8776 + faster-whisper GPU + 学习通 sidecar）+ 原生 Kotlin 安卓 APP。重本机、重离线、录音可靠、仅安卓。
- 发起人 Web 版：阿里云 Node 服务 + 浏览器/PWA。AI 助教在云、跨端即用、录音依赖浏览器。

## 二、必须满足的两个硬约束

1. 所有 UI 用发起人的 Web 设计（原生 Kotlin UI 约 9.4k 行退役）
2. 主形态是 APP，尽可能安卓 + iOS 都能用

## 三、决策

**选 A：Web UI 统一 + 云端后端为核心 + 原生壳承载录音。**

- 前端只维护一份：webapp/public（你的设计）
- 云后端：webapp（AI 助教 / EAMS / OCR / 课表）
- 他的电脑端不推倒：作为「能力端」整体保留（pc-agent），提供 GPU 转写、AI 成稿、学习通 v1、素材修复
- 安卓：WebView 壳加载云端 UI（先保安卓）；后续接原生录音桥
- iOS：先 PWA；有 Mac 后 WKWebView 壳

## 四、为什么不选 B / C

- B（保留原生 APP 只换皮 + 云 AI）：安卓体验最好，但**出不了 iOS**，直接违背约束 2。
- C（双轨：原生 + Web 并行）：两套 UI 两套逻辑，违背约束 1，维护成本双倍。

## 五、取舍（如实）

得到：双端可能、UI 统一、AI 常驻、只维护一套界面。
放弃：原作者的原生 UI、纯 Web 的录音可靠性、离线能力（需 P1/P3 补）。
风险：学习通必须本机在线；iOS 需要 Mac；移植量大。

## 六、模块职责

| 模块 | 职责 | 后续 |
|---|---|---|
| webapp | 唯一前端 + 云后端 + 学习通代理 | P1 落地上传协议；P2 补页 |
| pc-agent | 转写 / AI 成稿 / 学习通 v1 / 素材修复 / 更新清单 | 作为可选能力端，接口对齐 |
| app-android | WebView 壳 + 服务器地址切换 | P3 原生录音桥 |
| （旧版原生源码） | 不作为公开版一部分 | 仅内部留存参考 |
